## Guest experience

Title: **Chastity Vibrator**. Subtitle: **Choose a vibration level for the connected toy**.
Four controls: **5 seconds low / medium / high / max**. Fifth: **Hold for random — Release to stop**.
Dark phone layout, active progress, reduced-motion support, keyboard and pointer hold support.
Ready/running/stopped/EDGE/unavailable feedback is signed by the host's existing
ECDSA P-256 key, not inferred from a successful network send. No latency meter.
The existing signed EDGE-count message and verification format remain unchanged.

## Timing and safety

| Control | Peak device level | Original strength | Target envelope |
|---|---:|---:|---|
| Low | 4 | 20% | 500ms up, 4000ms peak, 500ms down |
| Medium | 8 | 40% | 500ms up, 4000ms peak, 500ms down |
| High | 12 | 60% | 500ms up, 4000ms peak, 500ms down |
| Max | 14 | 70% | 500ms up, 4000ms peak, 500ms down |

Integer ramp samples target 100ms intervals, using elapsed time rather than
adding Bluetooth write durations to the five-second deadline. The five-second
clock begins after the initial zero write. Radio/browser scheduling can add delay.
Stop and EDGE cancel the generation immediately and queue zero without a ramp.
Queued positive writes check their generation immediately before transmission.
An already submitted Bluetooth operation cannot be retracted; zero follows it.
All outgoing vibration commands are checked against level 14.

Randomness comes exclusively from host Web Crypto: integer levels 0–14 inclusive,
with independently selected dwell times of 200–900ms inclusive. Guest data never
sets an intensity. Each activation consumes fresh randomness.

While holding, the guest sends a heartbeat every 250ms. Signed host status issues
fresh random challenges every 500ms. Each challenge expires 1200ms after its
**host issuance**, so delayed/replayed packets cannot extend its lifetime. The
watchdog checks every 100ms: loss of valid holding evidence targets a stop within
1200–1300ms of the last usable challenge's issuance, plus Bluetooth scheduling.
Expired/stopped holds cannot be restarted by heartbeat. Duplicate start IDs are
rejected. Release arriving before start prevents that start. A session accepts at
most 10,000 unique command/release IDs; create a fresh session if that ceiling is reached.

Pointer release/cancel/lost capture, blur, pagehide, offline, and guest backgrounding
send release and stop heartbeats. Host backgrounding, channel failure, Stop and EDGE
stop the pattern. Reconnection sends only zero, never restarts a pattern.

**Hardware limitation:** this is a browser watchdog, not a firmware watchdog. If
Android kills/freezes the host before it transmits zero, or Bluetooth fails, browser
code cannot guarantee that the physical device stops. Keep the host visible and
retain access to the device's physical power control. Actual Android/device tests
remain required. The application does not claim otherwise.

## Four-character links: no guest account

The user chose four characters plus host approval instead of a longer direct link.
Format: `https://ctmp.uk/#ABCD` (example only). The bare domain also has a four-character
guest-code box. Codes accept either case and omit `0`, `1`, `I`, and `O`.
The fragment works with GitHub Pages without path rewrites; it is not sent in the HTTP
request to Pages. The guest name is kept out of the URL.

The four-character code locates a pairing queue and grants **no control access**.
A first-time browser requests approval with a fresh 192-bit request secret. The
guest and host see the same four-digit check number, which they confirm through
their existing private conversation before the host approves. The guest needs
no login, registration, email, or password. Merely guessing the short code can
submit a request, but cannot obtain control. Requests expire after ten minutes;
admission is atomically limited to ten requests per profile per ten-minute window.

Approval supplies an 80-bit private token (16 uniform base32 characters), which
the guest browser remembers in localStorage. Later visits through the same short
link reuse it. Private browsing, cleared storage, or another browser needs approval
again. The resolver exposes only the current fresh 192-bit session ID and public
EDGE verification key. No active session produces an unavailable screen, which polls
every five seconds. New sessions keep the profile/code and reset the EDGE count.

Replacing a link changes its short code and private token, removes its pairing
requests, and ends the active session. Old stored tokens fail resolution. Each host
has at most one current backend session. Host renewals run every ten seconds;
the backend expires an unrenewed session after 45 seconds. The host locally blocks
control after 30 seconds without renewal. A session revoked from another host
browser is stopped on renewal or local lease expiry (at most 30 seconds while JS runs).

## Authentication and database

Supabase email/password Auth, persistent refreshable host session, no signup UI.
Every host backend action calls `auth.getUser(jwt)` and checks the service-managed
`control_hosts` allowlist. Ordinary signup cannot authorise a host. Visitors see
login/code entry; host controls start hidden. Backend authorization is independent
of UI visibility. An authorised host can create, select, activate, end and rotate
guest profiles, and approve/deny browser requests.

Added tables: `control_hosts`, `control_guests`, `control_sessions`, `control_pairings`.
All have RLS and explicit service-role-only policies. No table grants to `anon` or
`authenticated`. Names, tokens, sessions, and pending requests cannot be listed
through the Data API by guests or ordinary users. Tokens are kept in service-only
storage for host link management; lookup uses an indexed SHA-256 digest.

Added Edge Function: `guest-access`. Gateway `verify_jwt=false` is intentional:
anonymous pairing/resolution is authenticated using capabilities and approval,
while **every** host action verifies the user JWT plus host allowlist in the function.
The service-role key is read only from Supabase's server environment. It is never
embedded in static files or committed. The existing publishable key remains public.

Added RPC: `request_control_pairing(uuid,text)`, SECURITY INVOKER, empty search path,
EXECUTE restricted to service_role. It serialises queue admission with a row lock.
No public directory, SECURITY DEFINER function, or new Realtime policy was added.
Realtime continues to use the existing unguessable session topics and signed host
messages. `noindex,nofollow,noarchive`, no-referrer metadata and robots.txt were added;
these discourage indexing and do not replace authentication or imply age assurance.

Migrations: `20260915072625_private_guest_access.sql` and
`20260915073058_guest_browser_pairing.sql`. Both and the Edge Function were deployed.
The security advisor returned no findings; database checks confirmed RLS on all four
tables and no anonymous/ordinary-user table or pairing-RPC access. Live unauthenticated
host actions returned 401; invalid guest tokens/codes yielded no access.

## Device test checklist (after account authorisation)

1. Open ctmp.uk in a private browser. Confirm only login and guest-code entry show.
2. Sign in as the authorised host on Android Chrome. Connect the existing Lovense
   device; verify the confirmed characteristic still connects and no vibration starts.
3. Save a named guest, share its four-character link and open it in another browser.
   Confirm no account is requested and controls are unavailable before approval.
4. Compare the check number over your private conversation, approve it on the host,
   and start a session. Refresh the guest: approval should be remembered.
5. Run each fixed button: confirm the original 20/40/60/70% peaks, smooth start/end,
   about five seconds overall, host-acknowledged active state and progress.
6. Replace a running fixed command with another; press host Stop during ramp-up and
   at peak. Verify immediate stop intent, no ramp-down and no delayed restart.
7. Hold random, release, slide off/cancel, switch guest apps, close the guest tab,
   and separately disconnect guest internet while holding. Verify prompt stop;
   network-loss stopping should occur around the documented heartbeat window.
8. Press EDGE during fixed and random commands. Verify immediate stop, a 30-second
   countdown, blocked guest commands and one signed counter increment. Press EDGE
   again: countdown restarts at 30 and counter increments once more. Host Stop works.
9. Let EDGE expire: controls become available without automatic vibration. Refresh
   the guest and check its count recovers. Start a fresh session: count resets.
10. Background/restore the host. Verify stop on background, existing-session recovery,
    realtime resubscription, wake-lock reacquisition, and no automatic vibration.
    Switch the device off/on; verify automatic GATT recovery or Reconnect Device.
11. End the session: the same guest link becomes unavailable. Start another session
    for that guest: the same link works. Rotate the link: the old code/token fails;
    a newly approved browser can use the replacement.
12. Open the short link in a different/private browser: require a new approval.
    Deny a request and verify it cannot control. Sign out of the host and confirm
    control ends and unauthenticated requests cannot create sessions or list guests.
